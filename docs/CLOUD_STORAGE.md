## Offline, migration and conflict behavior

Music is stored as individual `musicTracks/{videoId}` and `musicPlaylists/{slug}` documents, with the active IDs and revision in `musicCatalog/current`. All visitors can read this catalog; only allowlisted editors can publish it. One atomic publication writes tracks, lists and manifest. The client reads the manifest plus two bounded revision queries when opening Music, validates membership/content, and ignores outdated replies. No persistent catalog is written to IndexedDB. Optional music in a legacy full-library import is normalized during publication instead of being retained in the story JSON.

Private owner playlists remain at `users/{uid}/musicPlaylists/{playlistId}`. Explicit public sharing creates the matching `publicMusicPlaylists/{uid}_{playlistId}` projection with creator name and no email. Switching to private/hidden removes that projection atomically. System catalog lists and community-owned public lists have distinct counts in the UI; zero community lists does not mean the system catalog is missing.

Daily learning adds two private owner-only collections: `users/{uid}/studyDays/{localDay}` freezes the chosen story and up to five due vocabulary IDs and stores reading completion; `users/{uid}/quizAnswers/{encodedAnswerId}` stores immutable per-question evidence, grouped by attempt UUID. No extra XP is awarded for notebook practice. Additive IndexedDB migrations and backups include both collections; old backups remain readable. Earlier daily plans win across devices, preserving reading completion for the chosen story. Question content changes start a fresh mistake history; old events remain available in the account backup. These owner-only permissions were tested on the emulator and included in the 16 October production Rules release.

- Legacy `hanzigo` IndexedDB remains the guest cache. Registered users have separate `hanzigo-account-{uid}` caches and persistent outboxes. A signed-in account's cache is never copied into another account.
- Old browser learning data is claimed once by the first account after this migration. Linking a current guest into a new registered account carries its learning forward. Guest data is retained. Historical browser-only data had no owner UID, so this one-time claim represents the current browser's migration, not proof of past ownership.
- Migration only initializes missing cloud preferences; it does not replace settings already saved by an existing account with guest defaults. Explicit edits remain queued by account UID, including through reload.
- Progress keeps completed=true and the highest quiz result even when an older browser sends its position later. Unique activity IDs prevent duplicate XP. Mutable rows choose the latest client updatedAt; exact timestamp ties choose a deterministic record. These are learning UX records, not trusted evidence for financial rewards or secure milestone unlocks.
- Listener replies, queued writes, preference hydration and imported backups stay associated with their original account, even if the user switches accounts while work is in flight.
- Library content is validated before publication and on receipt. An atomic transaction merges a single story into the latest library so two editors updating different stories do not discard each other's work. The published library is stored as validated JSON (800 KB UTF-8 cap); larger libraries need sharding. Cached cloud content and bundled content provide offline/failure fallback.
- Private editor drafts stay separate from the public library until the admin publishes. Draft cache and legacy default-recipient migrations are claimed once by the first authenticated editor; an existing cloud default is preserved.

## Initialization and rollback

`npm run firebase:seed -- --project hanzigo-eea7d` uses the existing Firebase CLI session on the trusted developer machine. No tokens/service-account keys enter source, frontend bundles, or backups. It creates `content/library` only if absent, using an atomic exists=false precondition; if the library exists it validates and preserves it. CLI updatedBy is a generic bootstrap marker.

Active production Rules were backed up locally at `/tmp/hanzigo-cloud-predeploy-rules.json`; existing indexes at `/tmp/hanzigo-cloud-predeploy-indexes.json`. The Rules backup contains the previous ruleset name and source. No existing user/message records or allowlist entries were changed. Rollback of a future approved Rules release restores that source and redeploys only Rules; preserve library/account documents rather than deleting data.

## Device cache policy

- Firestore explicitly uses memory-only caching. Cloud Music does not load the bundled song seed; the demo seed is a lazy import only without Firebase configuration. Music and seed chunks are excluded from PWA precaching. Video/audio files are not downloaded into app storage.
- Keep one offline story snapshot, without music, capped at **512 KiB**. Old combined cached libraries are compacted on startup. The current 20-story snapshot measures **183 KiB** in Settings.
- The active account keeps small learning metadata needed for existing SRS/XP derivations and a durable outbox. After server hydration is confirmed, switching/logging out compacts inactive caches, retaining every pending record, outbox entry and editor draft. Unconfirmed/guest data is never deleted by this cleanup. Logging in again repopulates the cache from Firebase. Settings exposes the story byte count, queued-write count and an inactive-cache cleanup action.
- This is a bound on the story snapshot, not a claim that all browser storage is 512 KiB. Auth session storage, static app assets, active learning metadata and unsent work have separate purposes.

Migration: `node --import tsx scripts/publish-music-catalog.ts --project hanzigo-eea7d --profiles` previews; append `--apply` to execute. Writes have existence/updateTime preconditions and run atomically. The pre-normalization public library/manifest backup is `/tmp/hanzigo-before-normalized-music.json`; the pre-release Rules source is `/tmp/hanzigo-before-cloud-first.rules`. No Auth passwords, hashes or provider credentials are copied to Firestore or the app.
